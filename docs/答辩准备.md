## 二、常见答辩问题与参考答案

### 2.1 关于课题背景

**Q1: 为什么要做这个课题？现有 AFL 等工具为什么不够？**

A: 传统模糊测试以覆盖率为导向，关注的是"代码跑了多少行"，而不是"程序状态是否被充分探索"。数组越界漏洞的触发需要特定索引值（如负数、大于数组长度的值），即使覆盖率很高，如果测试用例没有覆盖到这些特定的索引值，漏洞就无法被发现。本文针对这个 gap，专门对数组变量的运行时状态进行建模和引导。

**Q2: 你研究的主要创新点是什么？**

A: 三个创新点：(1) 提出了数组变量状态引导的方法，在覆盖率基础上增加了状态维度；(2) 设计了数组状态多样性度量模型，能够量化测试对数组状态空间的探索程度；(3) 设计了面向数组边界的专用变异算子和两阶段变异策略。

### 2.2 关于方法设计

**Q3: 你是怎么给数组分配 ID 的？多个函数里同名数组会不会冲突？**

A: 使用 FNV-1a 哈希算法，将"函数名 + :: + 变量名"拼接后计算 32 位哈希值。因为包含了函数名，不同函数中的同名数组会得到不同的 ID。同一源码在多次编译中 ID 保持一致，保证了测试的可复现性。

**Q4: 你的状态多样性得分 SDS 有什么实际意义？**

A: SDS 衡量的是对所有可追踪数组的索引空间探索程度。当 SDS 较低时，说明大量数组索引未被测试到，需要增加边界值探测；当 SDS 较高时，说明基本覆盖已经完成，可以转入邻近区域的精细探索。它为变异策略的自适应调整提供了量化依据。

**Q5: 为什么用两阶段变异？一个阶段不够吗？**

A: 两阶段设计各有侧重。阶段一（边界值探测）用预定义的边界值快速覆盖所有关键区域——负值、零、边界值、严重越界值等。这是广度优先的探索。阶段二（邻近值探索）则是在已触发访问的值附近进行细粒度搜索。两阶段结合实现了"先广后深"的策略，比单一策略更高效。

### 2.3 关于工具实现

**Q6: 介绍一下你的 LLVM Pass 是怎么工作的？**

A: 本工具实现了两个 LLVM Pass。静态分析 Pass（ArrayAnalysisPass）遍历函数中的 GEP 指令，识别数组变量并计算影响力分数。插桩 Pass（ArrayInstrumentPass）在每个 GEP 指令之后插入对 \_\_afl\_report\_array\_state 函数的调用，传入 array\_id、索引值、访问类型（读/写）和行号。这样在程序运行时，每次数组访问都会自动记录。

**Q7: GEP 指令是什么？为什么用它来检测数组访问？**

A: GEP（GetElementPtr）是 LLVM IR 中用于计算内存地址的指令。对于数组操作，GEP 的结构天然暴露了访问模式：它有基地址指针和一系列索引参数。比如 `getelementptr [10 x float], ptr %arr, i64 0, i64 %idx` 就能直接告诉我们：这是对长度为 10 的 float 数组的访问，索引是 %idx。所以 GEP 是检测数组访问的最佳抓手。

**Q8: 多维数组你是怎么处理的？**

A: 在 LLVM IR 中，对二维数组 `matrix[3][4]` 的访问会生成两个嵌套的 GEP 指令——第一个用行索引取出子数组，第二个用列索引取出元素。我对这两个 GEP 分别插桩，在生成 ArrayID 时对内层追加 "#dimN" 后缀，使不同维度的索引操作被独立追踪和分析。

**Q9: 运行时库和 AFLGO 是怎么交互的？**

A: 通过反馈文件机制。运行时库的 `__afl_report_array_state` 函数记录数组访问状态，在程序退出时将 SDS 和香农熵写入 `/tmp/array_feedback.txt`。AFLGO 调度器在校准阶段读取该文件，通过综合得分函数将状态评分与 AFLGO 原有的距离评分融合，影响种子的变异能量分配和排队优先级。

### 2.4 关于实验

**Q10: 你的实验用了哪些测试程序？**

A: 实验使用了 4 个真实开源代码库：mjs（JavaScript引擎）、cjson（JSON解析器）、lrzip（压缩工具）和 libpng（PNG 图像库）。这些程序涵盖了不同类型和规模的软件，且数组操作密度各不相同：cjson 的 JSON 数组解析涉及大量索引操作，libpng 的图像行缓冲区处理也有密集的数组访问。相比前两个，mjs 和 lrzip 的数组操作相对较少。在实验中，分别对比了 AFLGO 基线和本文工具在 1 小时内的路径发现数量、覆盖率和独特崩溃发现数量。

**Q11: 1 小时发现在 4 个目标上只发现了几到十几个独特崩溃，效果算好吗？**

A: 对于 4 个真实开源项目而言，在相同的 1 小时测试时间内，本文工具相比 AFLGO 均有稳定提升。cjson 和 libpng 的提升尤为显著（各 +6 个独特崩溃），说明数组状态引导能够更有效地触发这些项目中与数组操作相关的漏洞。mjs 和 lrzip 增量较小（+3 和 +2），这也符合它们数组操作密度较低的特性。

**Q12: 你的工具和 AFLGO 有什么区别？**

A: AFLGO 是定向模糊测试工具，通过控制流图距离计算引导测试向目标区域靠拢，但它无法区分同一代码位置上的不同数组访问状态。本文在 AFLGO 基础上增加了数组状态多样性引导机制，形成了"控制流距离 + 数组状态多样性"的双重引导体系。具体来说，通过 LLVM Pass 插桩追踪数组访问的运行时状态，用 SDS 和香农熵量化状态探索程度，再与 AFLGO 的距离评分融合来指导种子调度。两者是互补叠加的关系——AFLGO 解决"去哪儿"的问题，本文工具解决"到了之后如何探索不同状态"的问题。

### 2.6 开放性问题

**Q15: 你这个工具还有什么可以改进的地方？**

A: 主要有三点：(1) 测试对象数量有限——当前只在 4 个开源项目上验证，需要在更多真实软件上评估；(2) 状态反馈与调度器的闭环集成不够紧密——当前通过文件传递评分，存在 I/O 开销，未来可用共享内存实现零开销实时反馈；(3) 数组类型覆盖不够全面——当前主要支持栈上数组和全局数组，对动态分配的堆数组支持有限。

**Q16: 你觉得模糊测试的未来发展方向是什么？**

A: 我认为有三大方向：(1) AI 驱动的智能化——用强化学习等方法自动学习最优变异策略；(2) 多维度融合——将覆盖率、状态空间、污点信息等多维反馈融合；(3) 专业化——针对特定类型漏洞（如本文的数组越界）设计专门的检测方法。

**Q17: 在实现这个工具的过程中，你遇到的最大困难是什么？**

A: 最大的困难是理解 LLVM Pass 框架的编程模型。LLVM 的 IR 类型系统、Pass 注册机制、Builder API 都需要深入学习。特别是 GEP 指令的语义和多维数组的处理方式，花了比较多时间去理解。

**Q18: 你如何证明越界崩溃确实是数组越界导致的？**

A: 通过分析崩溃输入值和源代码的对应关系。比如崩溃输入是 "40"，对应代码 `local_data[idx] = 1.5f;`，而 `local_data` 只有 10 个元素。索引 40 远超数组长度，可以确定为数组越界写入导致的段错误。

**Q19: HTTP 解析器测试用例的设计思路是什么？**

A: HTTP 解析器模拟了真实 Web 服务器中请求解析的常见缓冲区操作模式。设计时参考了 Apache 和 Nginx 等服务器的请求解析流程：先解析请求行（METHOD + URI + 版本号），再逐行解析请求头（name:value），最后根据 Content-Length 请求头读取消息体。每个阶段都使用了固定大小的缓冲区，且缺乏边界检查，构成了多层次的数组越界漏洞集合。该测试用例的特点在于：涉及多种数组类型（字符数组、结构体数组、结构体内的数字组成员）、输入格式为结构化文本而非简单整数，更贴近实际软件测试场景。

**Q20: 状态反馈信息是如何从运行时库传递给模糊测试调度器的？**

A: 通过文件通信机制。运行时库在每次程序执行结束后，将 SDS、归一化香农熵和已追踪数组数量写入反馈文件（默认路径 /tmp/array_feedback.txt）。AFLGO 调度器在校准阶段读取该文件，获取真实的状态探索进度，计算综合得分 Q = α·D' + β·S + γ·E。Q 值高的种子获得更多变异能量和更高的排队优先级。之所以采用文件通信而非共享内存，是因为文件方式与 AFLGO 的 fork-server 模型兼容——每个子进程独立写入文件，无锁竞争。在论文的不足部分也提到了这一点，未来可以基于共享内存实现零开销的实时反馈。

## 四、现场注意事项

- 语速适中，不要过快，每分钟约 200-250 字
