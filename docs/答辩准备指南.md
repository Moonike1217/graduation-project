## 二、常见答辩问题与参考答案

### 2.1 关于课题背景

**Q1: 为什么要做这个课题？现有 AFL 等工具为什么不够？**

A: 传统模糊测试以覆盖率为导向，关注的是"代码跑了多少行"，而不是"程序状态是否被充分探索"。数组越界漏洞的触发需要特定索引值（如负数、大于数组长度的值），即使覆盖率很高，如果测试用例没有覆盖到这些特定的索引值，漏洞就无法被发现。本文针对这个 gap，专门对数组变量的运行时状态进行建模和引导。

**Q2: 你研究的主要创新点是什么？**

A: 三个创新点：(1) 提出了数组变量状态引导的方法，在覆盖率基础上增加了状态维度；(2) 设计了数组状态多样性度量模型，能够量化测试对数组状态空间的探索程度；(3) 设计了面向数组边界的专用变异算子和两阶段变异策略。

### 2.2 关于方法设计

**Q3: 你是怎么给数组分配 ID 的？多个函数里同名数组会不会冲突？**

A: 使用 FNV-1a 哈希算法，将"函数名 + :: + 变量名"拼接后计算 32 位哈希值。因为包含了函数名，不同函数中的同名数组会得到不同的 ID。同一源码在多次编译中 ID 保持一致，保证了测试的可复现性。

**Q4: 你的状态多样性得分 SDS 有什么实际意义？**

A: SDS 衡量的是对所有可追踪数组的索引空间探索程度。当 SDS 较低时，说明大量数组索引未被测试到，需要增加边界值探测；当 SDS 较高时，说明基本覆盖已经完成，可以转入邻近区域的精细探索。它为变异策略的自适应调整提供了量化依据。

**Q5: 为什么用两阶段变异？一个阶段不够吗？**

A: 两阶段设计各有侧重。阶段一（边界值探测）用预定义的边界值快速覆盖所有关键区域——负值、零、边界值、严重越界值等。这是广度优先的探索。阶段二（邻近值探索）则是在已触发访问的值附近进行细粒度搜索。两阶段结合实现了"先广后深"的策略，比单一策略更高效。

### 2.3 关于工具实现

**Q6: 介绍一下你的 LLVM Pass 是怎么工作的？**

A: MyArrayPass 是一个 Function Pass，对每个函数做两件事：(1) 遍历函数中所有指令，找到 GEP（GetElementPtr）指令——这是 LLVM IR 中做数组访问的关键指令，提取数组名、类型、长度等信息；(2) 在每个 GEP 指令之后插入对 \_\_afl\_report\_array 函数的调用，传入 array\_id、索引值、访问类型（读/写）和行号。这样在程序运行时，每次数组访问都会自动记录。

**Q7: GEP 指令是什么？为什么用它来检测数组访问？**

A: GEP（GetElementPtr）是 LLVM IR 中用于计算内存地址的指令。对于数组操作，GEP 的结构天然暴露了访问模式：它有基地址指针和一系列索引参数。比如 `getelementptr [10 x float], ptr %arr, i64 0, i64 %idx` 就能直接告诉我们：这是对长度为 10 的 float 数组的访问，索引是 %idx。所以 GEP 是检测数组访问的最佳抓手。

**Q8: 多维数组你是怎么处理的？**

A: 在 LLVM IR 中，对二维数组 `matrix[3][4]` 的访问会生成两个嵌套的 GEP 指令——第一个用行索引取出子数组，第二个用列索引取出元素。我对这两个 GEP 分别插桩，这样就同时捕获了行索引和列索引。不过对于多维数组，我会在 array\_id 中加入维度信息来区分不同维度的 GEP。

**Q9: 运行时库和 AFL++ 是怎么交互的？**

A: 通过 AFL++ 的共享内存位图。运行时库的 `__afl_report_array` 函数将 `(array_id, index)` 对哈希后写入 `__afl_area_ptr` 指向的位图。AFL++ 引擎在每次执行后检查位图变化——如果某个数组访问导致了位图更新，AFL++ 会自动将对应的测试用例标记为"有趣"，加入种子队列。这样不需要修改 AFL++ 内核，就实现了状态感知。

### 2.4 关于实验

**Q10: 你的测试程序是自己写的，有没有在真实软件上测试过？**

A: 目前的实验主要用于验证方法的可行性。在自定义的测试程序上，工具成功识别了所有数组访问并触发了越界崩溃。未来计划在 OpenSSL、libpng 等真实项目上进行评估。但这不影响当前实验的有效性——实验的目的不是证明工具的生产力，而是验证方法和实现是否正确。

**Q11: 60 秒只发现 2 个崩溃，这个效果算好吗？**

A: 对于测试程序只有 4 个数组操作函数的规模来说，60 秒 2 个崩溃是相当好的结果。更重要的是，这些崩溃是由不同的数组越界条件触发的（索引 40 和长字符串输入），说明工具能够探索不同的越界路径。在实际项目中，预期会有更多发现。

**Q12: 你的工具和 AddressSanitizer 有什么区别？**

A: AddressSanitizer（ASan）是一种运行时检测工具，它在编译时插入边界检查代码，在程序运行时检测越界访问并报错。而本文的工具是引导模糊测试的——它不是为了检测越界，而是为了指导测试用例生成，让测试更有可能触发越界。两者可以互补使用：用本文工具生成测试用例，在 ASan 检测模式下运行。

### 2.6 开放性问题

**Q15: 你这个工具还有什么可以改进的地方？**

A: 主要有三点：(1) 状态建模可以更精细——当前用简单的索引槽位计数，可以引入信息熵模型；(2) 变异器的反馈闭环可以更紧密——当前变异器是预定义逻辑的，可以改为实时根据状态反馈调整策略；(3) 测试范围可以扩大到真实世界的软件项目。

**Q16: 你觉得模糊测试的未来发展方向是什么？**

A: 我认为有三大方向：(1) AI 驱动的智能化——用强化学习等方法自动学习最优变异策略；(2) 多维度融合——将覆盖率、状态空间、污点信息等多维反馈融合；(3) 专业化——针对特定类型漏洞（如本文的数组越界）设计专门的检测方法。

**Q17: 在实现这个工具的过程中，你遇到的最大困难是什么？**

A: 最大的困难是理解 LLVM Pass 框架的编程模型。LLVM 的 IR 类型系统、Pass 注册机制、Builder API 都需要深入学习。特别是 GEP 指令的语义和多维数组的处理方式，花了比较多时间去理解。

**Q18: 你如何证明越界崩溃确实是数组越界导致的？**

A: 通过分析崩溃输入值和源代码的对应关系。比如崩溃输入是 "40"，对应代码 `local_data[idx] = 1.5f;`，而 `local_data` 只有 10 个元素。索引 40 远超数组长度，可以确定为数组越界写入导致的段错误。
